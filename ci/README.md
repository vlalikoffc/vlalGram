# Сборка APK через GitHub Actions

Здесь лежит всё, что нужно, чтобы APK собирался на серверах GitHub — **без компьютера**.
Раннеры GitHub имеют полный интернет (Maven/Google), JDK 17, Android SDK и 4 ядра/16 ГБ RAM,
поэтому ничего «закидывать в репозиторий» не требуется.

## Что нужно сделать один раз

1. Файл `ci/workflow-apk.yml` **перенести** в `.github/workflows/build-apk.yml`.
   В браузере на телефоне: открыть файл → ✏️ (Edit) → в поле с именем файла заменить путь
   на `.github/workflows/build-apk.yml` → **Commit changes** (в ветку `master`).
2. Готово. Больше ничего настраивать не надо.

## Как запускать сборку

`github.com/vlalikoffc/vlalGram/actions` → слева **build-apk** → кнопка **Run workflow** →
выбрать модуль (`TMessagesProj_App`) и архитектуру (`arm64-v8a`) → **Run workflow**.

Сборка идёт ~40–120 минут (первый раз дольше). По окончании APK можно скачать двумя способами:

- из выпадашки **Artifacts** на странице запуска (придёт zip — распаковать на телефоне любым архиватором);
- со страницы **Releases** (`github.com/vlalikoffc/vlalGram/releases`) — там APK лежит файлом,
  скачивается и ставится сразу, без распаковки.

## Что внутри

- `build-apk.sh` — весь процесс: чистка диска, установка SDK/NDK 27.2.12479018/CMake,
  скачивание подмодулей (ffmpeg, boringssl, td, media и др.), сборка выбранного модуля, сбор APK в `out/`.
  Переменные: `MODULE`, `ABI`, `VARIANT` (например `VARIANT=afatDebug` для debug-сборки).
- `apply-secrets.sh` — подставляет ключи из Actions Secrets перед сборкой (в репозиторий они не попадают).
- `check-secrets.sh` — проверка «не попал ли секрет в коммит»: `bash ci/check-secrets.sh`
  (запускать перед push). Значения в выводе маскируются, заведомо публичные — в `ci/secret-allowlist.txt`.

## Официальные ключи или свои

Правила Telegram (core.telegram.org/api/terms):

- **2.1** — «You must obtain your own api_id for your application»: использовать официальные
  (или чужие) ключи в своём клиенте прямо запрещено.
- **2.3** — в названии приложения нельзя слово «Telegram» (исключение — «Unofficial Telegram»);
  `vlalGram` под это правило попадает.
- **2.4** — официальный логотип использовать нельзя (в исходниках он есть — при публикации менять).
- **1.4** — нельзя ломать базовую функциональность (ghost mode, сохранение самоудаляемых сообщений,
  скрытие статусов «прочитано»/«печатает» и т.п.) — вот это уже повод для настоящих санкций.
- **4.1–4.2** — при нарушении Telegram пишет в аккаунт, ответственный за приложение, даёт **10 дней**
  на исправление, после чего отключает доступ к API и уведомляет магазины приложений.

На практике:

| сценарий | что будет |
| --- | --- |
| Собрал официальный исходник без изменений, пользуюсь сам | Ровно официальный клиент, только собранный тобой. Проблем нет |
| Раздаю форк со своими фичами на официальных ключах | Нарушение 2.1; аккаунты, заходящие с неофициального клиента, могут попадать под наблюдение, а «засвеченный» api_id ловит `API_ID_PUBLISHED_FLOOD` |
| Свои api_id/api_hash с my.telegram.org (2 минуты, бесплатно) | Легальный сторонний клиент, класс проблем «чужой api_id» исчезает |
| Спам/флуд/ломание фич | Ключи тут не спасают — ограничения и блокировки аккаунтов |

Свои ключи храни в Actions Secrets — тогда их нет ни в репозитории, ни в истории (см. таблицу выше).

## Секреты: ключи живут вне репозитория

Проверено по факту: **своих ключей в репозитории сейчас нет**. `BuildVars.java`
(`APP_ID = 4`, `APP_HASH = 01…`), `release.keystore` (пароль `android`), все пять
`google-services.json` (проект `tmessages2`), `agconnect-services.json` и Maps-ключ в манифестах
**байт-в-байт совпадают с официальным репозиторием DrKLO/Telegram** — это публичные тестовые
ключи, они и так лежат в открытом виде в апстриме.

Если появятся свои (api_id/api_hash с my.telegram.org, свой keystore, свой Firebase-проект) —
их надо держать в **Settings → Secrets and variables → Actions → New repository secret**
и подставлять на сборке скриптом `ci/apply-secrets.sh`:

| Secret | Что это |
| --- | --- |
| `VLAL_APP_ID` | свой api_id (число) |
| `VLAL_APP_HASH` | свой api_hash |
| `VLAL_GOOGLE_SERVICES_B64` | `base64 -w0 google-services.json` от своего проекта |
| `VLAL_KEYSTORE_B64` | `base64 -w0 release.keystore` — свой ключ подписи |
| `VLAL_KEYSTORE_PASSWORD` / `VLAL_KEY_PASSWORD` / `VLAL_KEY_ALIAS` | доступы к ключу |

Секреты шифруются, в логи не попадают, форкам не отдаются. Значения в репозитории не появляются,
так что даже утечка кода их не раскрывает.

### Можно вообще ничего не настраивать

Без секретов сборка идёт на тестовых ключах Telegram: APK соберётся и заработает как официальный
клиент, собранный тобой (логин и чаты — ок). Свой `api_id` нужен в основном тогда, когда сборку
раздаёшь другим. Если решишь завести — с телефона, без терминала и без base64:

1. `my.telegram.org` → ввести номер телефона → код придёт в Telegram → войти.
2. **API development tools** → App title: `vlalGram`, Short name: `vlalgram`, Platform: `Android` → Create.
3. На открывшейся странице будет **api_id** (число) и **api_hash** (32 символа).
4. GitHub → Settings → Secrets and variables → Actions → **New repository secret**:
   имя `VLAL_APP_ID`, значение — число; затем второй секрет `VLAL_APP_HASH` со второй строкой.

`VLAL_KEYSTORE_B64` и `VLAL_GOOGLE_SERVICES_B64` можно не трогать вообще: подпись возьмётся
из тестового ключа в репозитории, Firebase — из тестового проекта (push-уведомления могут не
заработать, но сборка и логин от этого не зависят).

Если вписать в секреты что-то не то, сборка упадёт с понятным сообщением
(`VLAL_APP_ID должен быть числом…`), а не с загадочной ошибкой компиляции — проверки встроены
в `ci/apply-secrets.sh`.

## Раздача людям: что нужно сделать иначе

Если APK уходит не только тебе, меняется четыре вещи.

### 1. Свои api_id/api_hash — обязательно

Правило 2.1 требует свой `api_id`. Плюс это выгодно: если что-то в клиенте сочтут нарушением,
Telegram пишет **в твой аккаунт** и даёт 10 дней на исправление (п. 4.1). С официальными ключами
ты этого канала не имеешь вообще — ключи-то не твои.

### 2. Свой ключ подписи (keystore)

`TMessagesProj/config/release.keystore` в репозитории — **публичный** ключ из официального репо.
Он же используется для воспроизводимых сборок Telegram, и это значит: любой может подписать APK
с тем же `applicationId` и той же подписью, и он установится *обновлением поверх твоего*.

Поэтому для раздачи — свой ключ. Без компьютера он делается так: **Actions → build-apk → Run workflow**
с галкой **generate_keystore** → по окончании скачать артефакт `vlal-keystore` (файл
`release.keystore`, пароль — тот, что в секрете `VLAL_KEYSTORE_PASSWORD`). Храни его: без него
нельзя будет выпустить обновление «поверх» уже установленного приложения.

### 3. Собирать standalone-вариант

`TMessagesProj_AppStandalone` + `afatStandalone` даёт отдельный `applicationId`
(`org.telegram.messenger.web`), поэтому APK ставится **рядом** с официальным Telegram:
никого не надо просить удалять свой Telegram и не ломается их подпись.

### 4. Переименовать и сменить логотип

- Название: строка `AppName` в `TMessagesProj/src/main/res/values*/strings.xml`
  (в 2.3 запрещено слово «Telegram» в названии; исключение — «Unofficial Telegram»).
- Иконка: `TMessagesProj_AppStandalone/src/main/res/mipmap-*/ic_launcher_sa.png` и
  `ic_launcher_sa` в `mipmap-anydpi-v26` (п. 2.4 — официальный логотип нельзя).
- Плюс п. 2.2: в описании/интро стоит упомянуть, что приложение использует Telegram API.

Что ещё понадобится: свой Firebase-проект (иначе push-уведомления у чужих устройств не заработают) —
`google-services.json` → секрет `VLAL_GOOGLE_SERVICES_B64`.

### Как передавать APK

Релизы и артефакты в **приватном** репозитории скачиваются только с авторизацией — друзьям по ссылке
не отдастся. Варианты: выкладывать APK в свой Telegram-канал/чат (логично для такого проекта),
либо сделать репозиторий публичным (тогда ключи уже должны быть в Secrets, а из истории убрано лишнее).

### Чего не делать

Пункт 1.4 (не ломать базовую функциональность): ghost mode, сохранение самоудаляемых сообщений,
подмена «прочитано»/«печатает». Это единственная категория, где санкции летят не по правилам
о ключах, а по-настоящему — в том числе аккаунтам тех, кто таким клиентом пользуется.

## Можно ли сделать репозиторий публичным?

Можно — и тогда Actions станут **безлимитными** (публичные репо: минуты не считаются на стандартных
раннерах; приватные на бесплатном плане: 2000 минут в месяц, то есть ~15–25 таких сборок).

Если решишь открывать:

1. Убрать секреты из кода (см. таблицу выше) — то, что лежит в файлах, публикация раскроет вместе с историей.
2. Удалить тег `old-history` (старая 606-коммитная история) — иначе она останется доступной на GitHub.
   Локальная копия старой истории при этом никуда не денется (`git tag old-history` в своём клоне).
3. Если свой api_hash когда-либо где-то засветился (в истории, в чужом репо, в чужом клиенте) —
   пересоздать приложение на my.telegram.org: api_hash нельзя «сбросить», только удалить приложение и создать новое.
4. Бонус публичного репо: бесплатный secret scanning (письмо, если секрет попал в коммит) и push protection.
5. Firebase-ключ (`google-services.json`) — не секрет: он всё равно лежит внутри APK.
   Ограничивать его надо в Google Cloud Console: package name + SHA-1 сертификата приложения.

Альтернатива, если хочется безлимитных минут, но без публикации кода: публичный репозиторий-раннер
(пара строк workflow, клонирующий приватный репо по токену из своих Secrets) — результат складывать
в релизы приватного репо, чтобы APK не оказался публичным.


- Приватный репозиторий на бесплатном плане: **2000 минут Actions в месяц**. Одна сборка ~1–2 часа,
  то есть примерно 15–25 сборок в месяц бесплатно.
- Кэш Gradle (10 ГБ на репозиторий) ускоряет повторные сборки: первый раз ~10 мин на зависимости, дальше меньше.
- Хранилище артефактов: 500 МБ. Один arm64 APK ~60–90 МБ, старые артефакты чистятся сами (retention 30 дней).
- Если нужны все 4 архитектуры (`ABI=all`) — сборке нужно сильно больше места и времени;
  на стандартном раннере это обычно падает по диску.
